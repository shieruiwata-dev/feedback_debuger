# 実装時の判断と理由

要件で「実装時に決定してよい」「理由を明示すること」とされていた点、
および要件から意図的に外した点をまとめる。

---

## 1. 埋め込みベクトルの生成元を Dify ではなく OpenAI にした

**判断**: 分類は Dify のワークフロー API、埋め込みは OpenAI の `/v1/embeddings` を直接呼ぶ。

**理由**:
Dify が公開している API は「アプリ（チャットフロー / ワークフロー）を実行する」ものであって、
任意テキストをベクトル化する汎用 embeddings エンドポイントは提供されていない。
Dify の中で埋め込みが使われるのは Knowledge（RAG）の内部処理としてであり、
そのベクトルを外から取り出して pgvector に入れる正規の口が無い。

要件も「Difyまたは別経路で埋め込みベクトル生成を追加し」と別経路を許容しているため、
既定を OpenAI 直呼びにした。

**逃げ道**: `EMBEDDING_PROVIDER=dify_workflow` にすると、
`embedding` という出力変数に数値配列を返す Dify ワークフローを使う経路に切り替わる。
Dify 側でコードノードを書いて外部の埋め込み API を叩くような構成にしたい場合に使える。

**代償**: AI の課金経路が Dify と OpenAI の 2 つになる。
分類と埋め込みでモデル提供元が別々になるので、障害時の切り分け先も 2 つになる。

---

## 2. 代表ベクトル（representative_embedding）は重心で更新する

**判断**: クラスタに item が増えるたび、所属 item の埋め込みの**平均（重心）**で貼り直す。
要件が提示していた「変更しない」「既存と新規の平均」の後者に近いが、
逐次的な 2 点平均ではなく毎回全メンバーの平均を取り直す実装にした。

**理由**:

- **固定にしない理由**: クラスタの代表ベクトルが「最初に届いた 1 件の言い回し」に固定されると、
  同じ問題を別の言葉で書いた後続の意見が閾値を超えられず、クラスタが不必要に分裂する。
- **逐次平均にしない理由**: `(既存 + 新規) / 2` を繰り返すと、
  直近に入った item ほど重みが指数的に大きくなる（古いメンバーの寄与が半減し続ける）。
  取り込み順という本質的でない要因でクラスタ中心が動いてしまう。
- 毎回 `avg(embedding)` を取り直す方式なら、順序に依存せず全メンバーが等しく寄与する。
  pgvector が `avg(vector)` 集約を持っているので SQL 1 文で書け、
  クラスタあたりの件数はたかだか数百件なのでコストも問題にならない。

**代償**: クラスタが大きくなるほど中心が平均に寄り、意味の広いクラスタに育ちやすい。
「1 つのクラスタに雑多な意見が吸い込まれる」現象が出たら閾値を上げる。

---

## 3. 代表要約（representative_summary）は初回の値を維持する

**判断**: クラスタ作成時の要約を固定し、item 追加時に書き換えない。

**理由**: ダッシュボードの見出しが更新のたびに変わると、
「昨日見たあの項目」を追えなくなりトリアージの体験が壊れる。
また、書き換えるたびに要約生成の LLM 呼び出しが必要になり、コストと遅延が増える。

**代償**: クラスタの中身が育つと、初回要約が代表として不適切になることがある。
必要になったら「item_count が一定を超えたら代表要約を再生成する」バッチを足すのが素直。

---

## 4. スコアの正規化は min-max ではなく「最大クラスタ = 100」の比例スケール

**判断**:

```
score = (100 × item_count ÷ 同一app内の最大item_count) × priority_weight
```

**理由**: 要件が例示した min-max（最大 = 100 / 最小 = 0）だと、
**最小件数のクラスタのスコアが必ず 0 になる**。
その結果「1 件しか届いていないが urgent なバグ報告」が優先度重みに関係なく最下位に落ちる。
比例スケールなら件数の比がそのままスコアに反映され、優先度重みも効く。

**代償**: 最大クラスタが 1 件しかない初期状態では、全クラスタが score 100 × weight に張り付く。
データが溜まるまでは順位がほぼ優先度だけで決まる。

---

## 5. クラスタの priority は「最頻値」ではなく「最高値」

**判断**: クラスタ内 item の優先度のうち最も高いものを採用する（`priority_rank()` で比較）。

**理由**: 見落としのコストが非対称だから。
10 件中 9 件が low でも 1 件が urgent なら、
それは「多くの人が軽く感じているが、ある状況では業務が止まる」問題であり、
埋もれさせるより目立たせた方が損失が小さい。

**代償**: 分類の誤りが 1 件混ざるだけでクラスタ全体が urgent に昇格してしまう。
誤検知が目立つようなら最頻値に変える（`refresh_cluster_aggregates()` の 1 箇所の変更で済む）。
category は逆に最頻値を採用している（こちらは非対称性が無いため）。

---

## 6. 同時挿入は app 単位のアドバイザリロックで直列化する

**判断**: `assign_item_to_cluster()` の冒頭で `pg_advisory_xact_lock(hash(app_id))` を取る。

**理由**: 似た意見が同時に 2 件届くと、両方が「既存クラスタなし」と判定して
同じ内容のクラスタを 2 つ作ってしまう（read-then-write の競合）。
`app_id` 単位のロックなら、別アプリの取り込みは並列のまま走り続ける。

**代償**: 同一アプリへの取り込みがクラスタリング処理の分だけ直列化する。
1 件あたりの処理は数十 ms なので、社内ツールの流量では問題にならない想定。

---

## 7. external_id の unique 制約は `(source_type, external_id)` の複合

**判断**: 要件は「external_id に unique 制約」だったが、
`(source_type, external_id)` の複合部分ユニークインデックス（`external_id is not null` の行のみ）にした。

**理由**:

- 単独 unique だと、`external_id` が NULL の行を複数持てるかどうかが分かりにくい
  （Postgres では NULL 同士は重複扱いされないので実は複数持てるが、意図が読み取れない）。
  部分インデックスにして「NULL は対象外」を明示した。
- ソース種別ごとに ID の名前空間が違う（Slack の `C123:1754300000.000100` と
  メールの Message-ID）ため、偶発的な衝突を型レベルで避けられる。

---

## 8. feedback_clusters に status 列を追加した

**判断**: 要件のスキーマ定義には無いが `status` 列を足し、
`set_cluster_status()` RPC でクラスタと配下 item の両方を更新する。

**理由**: 要件のフロント仕様に「ステータス変更をクラスタ単位で更新できる UI」があるが、
クラスタ側に status が無いと「配下 item のステータスの集計値」を毎回計算する必要があり、
item ごとにバラバラの値になったときの表示が定義できない。
クラスタを真とし、変更時に配下へ伝播させる方が状態が一意になる。

同様に、要件外だが `feedback_items` に `processing_state` / `processing_error` / `processed_at` を追加した。
Dify や埋め込み API が落ちたときに、どこまで処理できたかを記録して再開できるようにするため。

---

## 9. AI エンリッチメントは環境変数で ON/OFF する

**判断**: `ENABLE_AI_ENRICHMENT` が false の間は「受信 → 正規化 → そのまま insert」で止まる。

**理由**: 要件の実装順序が
「Step 2: 分類・クラスタリングなしで先に動かす → Step 5-8 で AI を足す」
となっているため、コードを書き換えずにその段階を再現できるようにした。
本番運用中に Dify が落ちたとき、取り込みだけ生かして AI を切る、という緊急対応にも使える。

---

## 10. AI 処理はレスポンスを返した後にバックグラウンドで実行する

**判断**: insert 直後に `EdgeRuntime.waitUntil()` で enrichment を投げ、
HTTP レスポンスは待たずに返す。

**理由**: Slack Events API は **3 秒以内**に 200 を返さないとリトライを送ってくる。
Dify の分類は数秒かかるため、同期実行するとリトライが多重発火し、
同じメッセージの取り込みが重複する（unique 制約で弾けるが無駄な負荷になる）。

**代償**: バックグラウンド処理が失敗しても HTTP レスポンスには現れない。
そのため `processing_state = 'failed'` を残し、`process-feedback` の
`mode=pending` で回収する仕組みを併せて用意している。

---

## 11. レートリミットは Postgres で数える

**判断**: Redis や Upstash を持ち込まず、`rate_limit_hits` テーブルと
`check_rate_limit()` 関数で数える。

**理由**: 使用技術を Supabase / Dify / Lovable に閉じるという前提があり、
社内ツールの流量（1 日数十〜数百件）に対して Postgres で十分間に合う。
インフラを 1 つ増やすコストの方が大きい。

**代償**: 投稿ごとに 2 回の RPC（短期・長期ウィンドウ）が発生する。
流量が桁違いに増えたら、Edge Function 側のインメモリカウンタや専用ストアに移す必要がある。

**フェイルオープンにしている点**: `check_rate_limit()` がエラーを返した場合は投稿を通す。
レートリミッタの障害で正規のフィードバックが落ちる方が損失が大きいと判断した。

---

## 12. anon の INSERT ポリシーは用意するが、推奨経路は Edge Function

**判断**: 要件どおり `feedback_items` への anon INSERT ポリシーを作ったが、
`FeedbackWidget` は anon キーを使わず、公開 Edge Function に素の `fetch` で投げる。

**理由**:

- anon 直 INSERT だとレートリミットも `app_slug` 解決も効かず、
  DB に直接スパムを流し込める。
- 埋め込み先の自社サイトに Supabase の anon キーを配る必要が無くなる。
- ポリシー側では `source_type = 'form'` と、
  AI が埋める列（summary / priority / category / embedding / cluster_id）が
  すべて NULL であることを `with check` で強制している。
  anon が「urgent のバグ」を騙って高スコアのクラスタを作ることはできない。
- `select` / `update` / `delete` は GRANT ごと落としてあるので、
  anon は自分が入れたデータすら読み返せない。

---

## 13. ダッシュボードはクラスタと item をクライアント側で結合する

**判断**: 選択中アプリのクラスタ（最大 500）と item（最大 3000）をそれぞれ取得し、
ブラウザ側で結合・フィルタする。

**理由**: `source_type` フィルタはクラスタ自身の属性では判定できず、
「配下 item に該当ソースが 1 件でもあるか」を見る必要がある。
サーバー側でやるなら専用のビューか RPC が要るが、
社内ツールの規模ではクライアント結合の方が単純で、
クラスタ展開時の item 表示も即座に返せる。

**代償**: 上限を超える規模になったら破綻する。README の「既知の弱点」に明記した。

---

## 14. メール経路を実装していない

**判断**: 依頼者の指示（「メールやっぱいらない」）によりスコープから外した。

要件では受信サービス（Cloudflare Email Routing / Resend Inbound / Postmark Inbound 等）を
選定して理由を明記することになっていたが、経路自体が不要になったため選定も行っていない。

**残してあるもの**: `source_type` の `'email'`、フロントの型定義とソースフィルタ、
ダッシュボードのメールアイコン。後から足す場合、
`_shared/ingest.ts` の `ingestFeedback()` に正規化済みデータを渡すアダプタを 1 本書けば繋がる。
